Audit: 2026-11-20. **No migration, database read/write, server startup, import or deployment was performed.** SQL Server production configuration is established from code, not an actual production connection. Backend source is available; production schema/data and deployment parity are blocked pending authorized operational evidence.

## Required migration procedure for a later authorized phase

1. Obtain sanitized deployed version/schema/cohort inventory and verify database target, provider, backup coverage and shared-host boundaries. No raw credentials or personal purchase export belongs in these docs.
2. Approve an additive schema and mapping plan, including legacy/default semantics, stable subject identities, purchased scope and immutable content/attempt revisions.
3. Produce a dry-run report on a restored clone: row counts, foreign-key orphans, duplicate import keys, purchase amounts/scopes, entitlement intervals, attempt/result hashes and note/page coordinates. Expected financial/history changes must be explicitly zero unless individually approved.
4. Verify backup restoration on the clone with agreed RPO/RTO. Compare full purchase/grant and progress/history invariants before/after migration. Exercise both old and new application readers.
5. Stage independent data, functional and visual releases; retain a way to stop new starts/purchases while allowing old attempts/payment verification. Require a named release owner and explicit deployment approval.
6. Roll back application routing/feature activation first while retaining additive columns/tables and original snapshots. Do not automatically run destructive Down migrations. A database restore is a last-resort coordinated operation: payments and user writes since the restore point require reconciliation.

No production rollback duration or zero-downtime guarantee is asserted. These require infrastructure/backup evidence and a rehearsal. Detailed per-task rollback and tests are in [execution plan](PHASE_EXECUTION_PLAN.md).
